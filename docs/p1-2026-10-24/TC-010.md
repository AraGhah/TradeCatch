# TC-010 — Create secure billing portal sessions

Verified October 24, 2026. The existing implementation already creates a fresh
Stripe Billing Portal session for each authorized request; no runtime fix was
necessary. No static billing URL is used by the application.

The POST route verifies the signed session, stored session expiry/revocation,
organization membership and owner/admin billing role. Customer ID and mode come
from that organization's durable database binding. The browser may supply only
locale; customer, organization, mode and return-URL overrides are rejected.
Cross-site requests are denied and session creation is rate limited. Successful
responses are private/no-store and accept only validated Stripe session URLs.

Inactive owners/admins can open billing to recover payments without regaining
application feature access. Missing bindings, wrong modes, database failures and
provider failures fail closed. Return destinations use the configured site
origin, with English and French billing paths.

All 13 portal tests passed without skips. Added a two-organization/repeated-visit
test proving a fresh provider POST and correctly scoped lookup on each request.
The 33 PostgreSQL billing tests also verified the durable customer binding from
webhook through portal creation. Changed-test ESLint passed.

Scope: synthetic Stripe session responses and test authentication, plus the
isolated PostgreSQL integration. Live portal configuration and a real Stripe
session were not exercised. Deploy and verify live configuration through the
normal release process; no production billing actions were performed.

Reference: https://docs.stripe.com/customer-management/integrate-customer-portal .
