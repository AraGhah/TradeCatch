# TC-009 — Synchronize Stripe subscriptions

Verified October 24, 2026. The existing implementation satisfies the requested
subscription synchronization behavior; no runtime change was necessary.

Signed, mode-matched subscription and invoice events reconcile current Stripe
customer/subscription state under a per-customer database lock. The receipt,
customer binding, subscriptions, organization plan and access status commit
together. Failed retrievals or database writes roll back the receipt so Stripe
can retry. Duplicate events are acknowledged after committed synchronization.

Configured prices determine Starter/Growth access. Active and trialing
subscriptions enable access; past-due, unpaid, incomplete and paused subscriptions
suspend it. Effective cancellation revokes access, while scheduled cancellation
and an active replacement retain the appropriate access. Tenant requests use
the stored organization state rather than a stale cookie plan.

Added verification for pause/resume, payment success/action-required events,
and an active replacement on a later Stripe subscription page. All 33 billing
tests passed against isolated local PostgreSQL, without skips. Existing tests
also cover duplicate delivery, rollback/retry, unknown prices, test/live and
organization boundaries, cancellation, recovery and durable portal linkage.

Scope: synthetic Stripe responses and signed local webhook requests. Live Stripe
webhook registration, price/key settings and real customer billing were not
changed or verified. The existing pinned Stripe API version was retained.

Reference: https://docs.stripe.com/billing/testing and
https://docs.stripe.com/billing/subscriptions/webhooks .
